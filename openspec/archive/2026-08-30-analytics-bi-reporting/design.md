## Context

Holding-level consolidation and project autonomy both require timely, accurate reporting across finance, procurement, inventory, and F&B operations. The SRS defines seven role-targeted reports with real-time and scheduled delivery, a < 2 second bulk report performance target, and bilingual (English/Arabic) output. See proposal.md - Why for motivation.

## Goals / Non-Goals

**Goals:**
- Seven SRS-defined reports with role-targeted audiences.
- Real-time and scheduled delivery with daily alerts.
- Bulk report performance under 2 seconds.
- Bilingual English/Arabic rendering.

**Non-Goals:**
- Ad-hoc drag-and-drop BI authoring (deferred).
- Predictive analytics or ML forecasting.
- External BI tool embedding (e.g., Power BI) in this phase.

## Decisions

- **Reporting service over a read model**: Reports query a denormalized read model fed by transactional events, rather than the OLTP schema. Rationale: meets the < 2 second bulk report target without impacting transactional performance. Alternative: direct OLTP queries — rejected for performance and coupling.
- **Pre-aggregated metrics for real-time reports**: Real-time reports (stock valuation, PO balances, menu margins) use incremental aggregates updated on each event. Rationale: real-time freshness with bounded query cost. Alternative: on-demand aggregation — rejected for latency.
- **Scheduled delivery via a scheduler service**: Daily/weekly/monthly reports and alerts are generated by a scheduler and delivered to role audiences. Rationale: the SRS specifies frequencies per report. Alternative: manual report generation — rejected.
- **Bilingual rendering via label localization**: Report labels and content render in English or Arabic based on user preference, with RTL layout for Arabic. Rationale: the SRS requires full bilingual support. Alternative: separate report templates per language — rejected for duplication.
- **Role-based report access**: Report availability follows the RBAC model from the security module. Rationale: reports are role-targeted per the SRS table.

## Risks / Trade-offs

- [Read model staleness] → Mitigation: event-driven refresh with lag monitoring.
- [Aggregate drift] → Mitigation: periodic reconciliation of aggregates against source data.
- [Arabic RTL rendering issues] → Mitigation: RTL-aware report templates and layout testing.

## Migration Plan

1. Deploy the read model and event consumers.
2. Build the report engine with pre-aggregated metrics.
3. Implement the seven reports in priority order (valuation, variance, PO balances first).
4. Enable scheduled delivery and daily alerts.
5. Add Arabic localization and RTL rendering.
